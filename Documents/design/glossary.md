# Glossary

Terms as used across the design docs in this folder, alphabetical. Where a term collides with an NRules or .NET term that means something related but different, that's called out explicitly — those are the ones most likely to cause confusion in code review.

**AEngineComponent** — ⚠️ **rejected design, kept for lineage.** The first-draft abstract base for governed, tiered game-logic components, adding `Tier` and `DependsOn` on top of `IEngineEventSubscriber`. Phase 2.6.5 **rejected the single-shared-base-class approach** in favour of each tier project owning its own identity type (`IRom` in `LunaFlow.Rom`, `IRuleBook` in `LunaFlow.Rulebook`), all implementing one minimal Engine-defined contract (`IHasDependencies`). Never implemented and won't be; the sketch survives in `engine-core.md` as the design's first draft. Its `DependsOn: IEnumerable<Type>` shape was likewise replaced — by `Provides`/`Requires` `Capability` lists.

**ARom** — ⚠️ **rejected design, kept for lineage.** The proposed abstract base every ROM module would derive from (`AEngineComponent` with `Tier => EngineTier.Rom`). Superseded by **`IRom`**, an interface in `LunaFlow.Rom`, for the reason above. See `IRom`.

**ARule** — `LunaFlow.Rules.ARule`, the base class every LunaFlow rule (hand-written or generated) derives from. Combines NRules' `Rule` (via the `NRule` global alias) with an `ILunaFlowReference`, so every rule is both loadable by NRules and traceable to a dotted path.

**BalancedRule** — the abstract rule tier used for anything that must respect game balance (as opposed to purely cosmetic player rules). Sits between `RuleBase` and `PlayerRule` in the sketch hierarchy in `architecture.md`.

**Cartridge** — the unit LunaFlow **publishes and consumes**: a **contract surface** (types anyone may name, in its own assembly) plus an **implementation** (one or more ROMs, one or more assemblies) that nothing outside may name. A ROM is an interchangeable part; a Cartridge is the thing that ships. The metaphor is literal — a cartridge is a memory chip plus the pinout that makes it usable, and the console binds to the pinout, never the chip. Exists for two reasons that converge on the same shape: the tier stack is a **trust boundary** (nothing may obtain anything by reaching *up*, since a deep layer that pulls from a shallow one inherits its trust level — eventually script), and a ROM must be replaceable without recompiling what sits above it. Today it is a **reference discipline**, not a runtime type. See [`cartridge.md`](cartridge.md).

**Contract surface** — a Cartridge's published assembly: the interfaces others bind to, and the same vocabulary the Cartridge's own ROMs use to talk to each other. Also serves as the Cartridge's **manifest** — a .NET assembly already carries complete type metadata, so a sidecar manifest file would duplicate it and drift. See [`cartridge.md`](cartridge.md).

**Capability** — `LunaFlow.Engine.Components.Capability`, a `record Capability(string Name, Type ContractType)`. The mediation point that lets peer components depend on each other **without a direct assembly reference**: a component advertises what it `Provides` and declares what it `Requires`, and the registry matches them by `Name`. `Name` is enforced-unique across a registry. `ContractType` is required at construction but currently **inert** — nothing reads it yet, because its consumer is the capability broker, which Phase 2.6.5 did not ship (see `IInteropRom`). Deliberately small, with room to grow metadata later without a redesign.

**ComponentRegistry** — `LunaFlow.Engine.Components.ComponentRegistry`, the explicit, hardcoded-by-design registry and load-time validator for ROM/Rulebook components. `Register(component, tier, name)` — no reflection-based discovery; the composition root lists modules by hand, same spirit as `RuleEngineOptions`. `Validate()` checks the complete graph as a unit rather than incrementally: duplicate capability providers, unsatisfied requirements, tier-ordering violations, and dependency cycles. Every failure is a hard load-time `InvalidOperationException` — fail fast, never silent degradation. A component's registered `name` **is its identity** within a registry and is unique; `Register` rejects a duplicate.

**EngineTier** — the enum (`Rom`, `Rulebook`, `WorldModule`, `GmOverlay`, `Player`) in `LunaFlow.Engine.Components`, tagging a registered component with its place in `architecture.md`'s layered stack. Sized for the full stack from the start; `WorldModule` gained a real consumer at Phase 2.8 (see `world-module.md`) and the tier question for `GmOverlay` is designed in `gm-overlay.md`, but `GmOverlay` and `Player` have no registered component yet. Real and load-bearing: `ComponentRegistry.Validate()` rejects a component whose required capability is provided by a **higher** tier, and the tier relationship decides *how* a dependency is expected to resolve — same-tier means capability-mediated through a broker, downward means a direct reference is fine. Peers may depend on each other, but only through a `Capability`, never a direct project reference. *(The second intended use — ordering `OnTurnAdvance` delivery so lower tiers settle before higher ones — remains unbuilt; see `IEngineEventSubscriber`.)*

**Fact** — NRules terminology, used as-is: an object inserted into a rule session (`session.Insert(fact)`) that rules can match against. Not a LunaFlow-specific type.

**Game system** — ⚠️ **the term collides; this entry is the ruling.** In LunaFlow, **the ROM *is* the game system** — the difference between playing D&D and playing Monopoly, an entirely different fact vocabulary and set of mechanics. A **Rulebook** is the *setting* built on top of one or more ROMs ("the Land of Oz version of D&D"). See "System, setting, and session" in `architecture.md`, which this entry pins.

A now-deleted `IGameSystem` interface in `LunaFlow.Rules` defined the term the **opposite** way — "a named system made up of one or more rulebooks," a container *above* Rulebook — and was removed 2026-07-26 (ticket [0031](../ClaudeWiki/Processes/Handoffs/0031-code-currency-vs-2-6-5-design.md)). It was unused public surface predating the settled vocabulary, and it could never have resolved its own `Books` type: the honest type is `IEnumerable<IRuleBook>`, but `IRuleBook` lives in `LunaFlow.Rulebook`, *above* `LunaFlow.Rules` — typing it correctly would have inverted the layer order. Recorded here rather than left as tribal knowledge, because "a collection of rulebooks" is an intuitive-sounding idea that will occur to someone again. If it's ever genuinely wanted, it's the config-driven packaging concern `non-goals.md` already defers with a named trigger, and it belongs **above** the Rulebook tier.

**GeneratedRuleReference** — the `ILunaFlowReference` the rule-pipeline generator assigns to every generated rule (`LunaFlow.Rules.GeneratorServices`, `public`). Flat dotted-path `FullPath` (`GroupName.RuleName`), no real `Parent`/`Subreferences` chain — same simplicity tier as Nine Rooms' hand-written `NineRoomsReference`. See rule-pipeline.md's D3 decision.

**GeneratorServices** — the `LunaFlow.Rules.GeneratorServices` namespace: the rule-authoring pipeline (parser → IR generator → compiler) described in `rule-pipeline.md`.

**GM / Storyteller** — the role that runs a live session: modifies world state, triggers events, uses the AI assistant. See the role table in `architecture.md`.

**GM Overlay** — a live, session-scoped rule or scripted change a GM makes during play (e.g. "Goblin 3 is unkillable," or "go directly to the Wizard, do not pass Go"), distinct from a World Module (which is authored ahead of time and reviewable). `EngineTier.GmOverlay` already exists in shipped code; the tier's contract and mechanism are designed in [`gm-overlay.md`](gm-overlay.md).

**IEngineEventSubscriber** — the future small interface (`OnStartup`, `OnTurnAdvance`, `OnResultFeedback`) for anything that wants to observe engine events without being a governed, tiered component. Wider net than `AEngineComponent`: a `Translator` or the AI assistant's narration layer would implement just this, not the fuller contract. See "Component model" in `engine-core.md`.

**IHasDependencies** — `LunaFlow.Engine.Components.IHasDependencies`: `{ IReadOnlyList<Capability> Provides; IReadOnlyList<Capability> Requires; }`. The one minimal, Engine-defined contract every governed component implements from its own project — `IRom` from `LunaFlow.Rom`, `IRuleBook` from `LunaFlow.Rulebook`. This is what replaced the rejected single-shared-base-class idea (see `AEngineComponent`). A Rulebook implementing it is **not** a violation of the "Rulebook never touches Engine primitives" rule — that rule governs authored content, not the tier's own infrastructure type joining the module system; see `engine-core.md`.

**IInteropRom** — `LunaFlow.Rom.IInteropRom : IRom`, the named marker for a ROM acting as **capability broker**: the component that aggregates capabilities advertised across loaded ROMs and resolves a peer's `Requires` against them. Kept as its own interface rather than folded into `IRom` for discoverability, the same reasoning ticket 0015 used for `IMechanic`. ⚠️ **Marker only today — the broker behaviour does not exist.** Phase 2.6.5 shipped the interface empty; designing and building its actual surface is Phase 2.7 work, sized against real content rather than guessed at. Don't read the name as a description of something callable.

**IRom** — `LunaFlow.Rom.IRom : IHasLunaFlowReference, IHasDependencies`. Real type identity for a ROM module, replacing the folder-and-namespace-only convention that preceded it (before Phase 2.6.5, "does ROM A depend on ROM B" had nothing to check against). Carries publishing metadata — `Name`, `Credits` — plus the `Provides`/`Requires` capability lists it inherits. Deliberately **no version**: `non-goals.md` parks ROM versioning, and nothing reads one.

**Marker** *(also: Standing Rule, Guard)* — a fact type whose mere presence should suppress other rules, e.g. an `ExitGameMarker` that stops further turn processing once a game has ended. Enforced today by hand (`.Not<T>()` in a rule's `When()`); the rule pipeline's `[StandingRule]` attribute is meant to inject this automatically. See "Settling markers" in `engine-core.md`.

**Mechanic** — `LunaFlow.Rules.IMechanic : IHasLunaFlowReference`: an object that tracks or mutates multiple facts in a structured, hard-wired way, as opposed to a single declarative rule. A **category marker with no members of its own**, mirroring `ARule`'s shape exactly — and deliberately so: ticket 0015 ruled that the actual operations (dice rolling, check resolution, a future Physics ROM's trajectory math) belong on the concrete class implementing it, never on the shared contract, since baking one Mechanic's shape into `IMechanic` would make it unimplementable by the next one. `public` so a concrete Mechanic in `LunaFlow.Rom` can implement it across the assembly boundary. Live example: `D20ResolutionMechanic`.

**NRules** — the third-party declarative rule engine (`NRules.Fluent.Dsl.Rule`, `RuleRepository`, `ISession`) LunaFlow builds directly on top of. Not a LunaFlow type; see the [NRules docs](https://github.com/NRules/NRules) for its own vocabulary (Agenda Group, `When()`/`Then()`, etc.).

**PlayerRule** — the most restricted rule tier: cosmetic, sandboxed, scoped to `self`/`pet`/`emote` only. See `architecture.md`.

**Reference** *(`ILunaFlowReference`)* — the hierarchical identity every rule, mechanic, and fact is meant to carry: a dotted path like `MyRuleBook.Chapter(A).Subsection(s)`, with `FullPath`/`Path`, a `Parent`, and `Subreferences`. Used for tracing and organization, not for rule matching.

**ROM (Rule Object Model)** — the layer above the Core Library in `architecture.md`'s diagram: the game-domain types and calculations (`Player`, `WorldMap`, `CombatPhase`, a Physics ROM's trajectory/intersection math, a `Dice` object, etc.) built by a **ROM Developer** in C# — see that entry for how this role differs from a Rulebook Author. Meant to be **pluggable** — a Rulebook depends on whichever ROM modules it needs, not one fixed model. In the "system / setting / session" shorthand (`architecture.md`), the ROM **is** the game system itself — the difference between playing D&D and playing Monopoly; see `Game system` for why that distinction is worth guarding. A real project (`src/LunaFlow.Rom`) with a real identity type (`IRom`), holding the D20System and NineRooms modules today. Don't confuse it with `GameState`/`GameWorld`/`Session` in `LunaFlow.Engine.Game` — those are Engine-owned turn/session bookkeeping, still empty placeholders, not ROM content.

**ROM Developer** — the role that builds reusable ROM modules: object types and the mechanics for using them (e.g. a `Dice` object and how to roll it), with no particular game in mind. Distinct from a **Rulebook Author**, who decides *when and why* those tools get used for a specific game (e.g. "use `Dice` to decide how many monsters are in the room"). See "System, setting, and session" in `architecture.md`.

**Rulebook** — the top-level organizational unit of a specific, compiled game built on top of one or more ROMs (`IRuleBook`, in **`LunaFlow.Rulebook`** — relocated there from `LunaFlow.Rules` in Phase 2.6.5, since that project *is* the Rulebook tier rather than an example holder), containing rules and rule groups. In the "system / setting / session" shorthand (`architecture.md`), a Rulebook is the setting built on a ROM's system — "the Land of Oz version of D&D" as distinct from D&D's underlying mechanics. `IRuleBook : IHasLunaFlowReference, IHasDependencies` and carries `DependsOnRoms` (`IReadOnlyList<string>`), naming the ROM(s) it depends on. ⚠️ `DependsOnRoms` is **declared but not yet validated** — nothing checks that a named ROM is actually registered; that's Phase 2.7 work. **`IRuleGroup` did not move** and stays in `LunaFlow.Rules`, since ROM-tier rule authoring uses it too — don't conflate the two.

**Rulebook Author** — the role that builds this specific game's rules in C# — classes, combat sequencing, win conditions — by *using* ROM tools a ROM Developer already built, not by extending the ROM itself. The `Dice`-object example in `architecture.md`'s "System, setting, and session" section is the clearest illustration of the boundary between the two roles.

**RuleEngineOptions** — `GameEngineOptions.Rules`, the concrete, hardcoded-by-design mechanism for loading rule assemblies and seeding initial facts today: `FromAssembly`/`FromTypes` plus `Seed`, applied to `RuleEngine` at `GameEngineCore.Start()`. Defined in [`nine-rooms-spec.md`](../NineRooms/nine-rooms-spec.md). This is what "hardcoded ROM registration" means in practice, and it's deliberately *not* the same thing as the future `AEngineComponent`/registry model in `engine-core.md`.

**RuleGroup** — `[RuleGroup("Name")]`, the attribute marking a static class as a set of related `[RuleTemplate]`-attributed rules. Also the informal name for that class itself.

**RuleIR / RuleIRGroup** — the parsed, engine-agnostic intermediate representation of one rule / one group of rules, produced by an `IRuleParser`. See `rule-pipeline.md`.

**RuleCodeUnit / RuleCodeClass** — the generated-code stage of the pipeline: a `RuleCodeUnit` is one output file (namespace + using block + classes + registry method), a `RuleCodeClass` is one generated rule class within it.

**RulePrototype** — the author-facing DTO for describing one rule (`Name`, `WhenStatements`, `ThenStatements`, etc.) before it's parsed into `RuleIR`.

**Session** — ⚠️ **overloaded, watch for this in code and docs.** Two unrelated meanings:
  1. **NRules session** (`ISession`, `factory.CreateSession()`) — a compiled, running rule engine instance you `Insert`/`Update`/`Retract`/`Fire` facts against. This is what `LunaFlow.Engine.RuleEngine` wraps.
  2. **LunaFlow `Session`** (`LunaFlow.Engine.Game.Session`) — a single connected client's context (input history, local state), unrelated to NRules. Currently an empty placeholder.

  When a doc or comment says "session" without qualifying which one, check context — this repo will eventually have both kinds active at once.

**Translator** *(`IGameEngineTranslator`)* — the adapter between one transport (console, WebSocket, test harness) and the singleton engine (`GameEngineCore.Instance`). See `engine-core.md` and `interfaces.md`.

**World-Builder** — the role that authors zones, monsters, and encounters as data (JSON/YAML) plus limited scripting, without touching engine-level logic. See `architecture.md`.

**World Module** — a unit of world-builder-authored content (a region, faction, encounter set) — data plus optional embedded Lua, authored ahead of time and reviewable, as opposed to a GM Overlay (live, unreviewed, session-scoped). Example: "our visit to the Emerald City."

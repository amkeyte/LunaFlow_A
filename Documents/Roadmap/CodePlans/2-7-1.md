## Context

Phase 2.7.1 (`Documents/Roadmap/phase-2-7-1.md`) is content-only — no new framework capability —
built entirely on Phase 2.7's shipped Cartridge toolbox (`Capability`/`IRom`/`ComponentRegistry`,
the `LunaFlow.Cartridge` contract surface, `GeneratorServices`). It exercises three things the
GridMap/D20System pair couldn't reach: a third peer ROM inside one Cartridge, a capability
(`IChallengeSolved`) consumed by two independent peers, and a pure-sink ROM shape (`Requires` with
no `Provides`). Alongside that, it replaces 1.d20's single fixed monster and 6-room-fixed-challenge
layout with a randomized 9-challenge / 5-monster pool and a small loot/inventory system.

Confirmed with Kofi (PM) before starting:
1. This will break `tests/LunaFlow.EngineTests`'s compile (rekeyed flavor keys, single-monster →
   roster shape change, `RoomChallenge` gaining `MonsterId`). Baraka doesn't touch `tests/`; ship
   `src/`/`example/` to spec and flag a follow-up ticket for Nadia — same sequence as Phase 2.7's
   0037 → 0038 → 0044.
2. Session-start content-assembly (the randomization) lives in a new sibling type in
   `LunaFlow.Rulebook.OneD20`, not folded into `OneD20RulebookContent`.

## Two spec deviations (mechanism, not behavior — will ticket to Amara at handoff)

**1. `ChallengePromptRule` keeps its current shape; does not gain `Match<RoomChallenge>`.**
The spec's Mechanics section describes the combat-branch prompt as needing the rule to read the
room's `MonsterId` at fire time, seeding `RoomChallenge` as a real NRules fact and looking up
`Monsters[challenge.MonsterId].DescriptionKey` inside `Then()`. That mechanism isn't buildable:
generated `RulePrototype` code has no constructor/DI seam — the exact reason ticket 0043 retired the
old `Match<Room> → room.PromptKey` static-lookup pattern (`engine-core.md`'s stated general rule:
"any design that needs rule code to call a broker reintroduces the static global
`D20SystemContent.Configure` was"). A dictionary lookup for `.DescriptionKey` also only yields a
*key*, not resolved text — even a hypothetically-injected `Monsters` dict would still need
`flavorText[key]` inside generated code, which 0043 ruled out generally, not just for the case it
fixed.

Buildable, behavior-identical alternative: resolve `Monsters[assignedMonsterId].DescriptionKey →
flavorText[...]` once during session assembly (`Program.cs`, the same moment `RoomChallengePrompt`
is already seeded today), and seed the resolved string into `RoomChallengePrompt` exactly as today —
only the *source* of the text varies (per-session monster assignment vs. the fixed `"monster-desc"`
key). `ChallengePromptRule`'s generated shape is unchanged. Delivers the exact player-visible
behavior the spec describes, with no new DI-seam violation and no other rule in this spec needing
`RoomChallenge` as a live fact.

**2. `LookCommandHandler` (GridMap) takes a per-room monster-max-HP lookup, not a scalar.**
Today: single `monsterMaxHp: int` (one monster existed). With a 5-monster roster, max HP varies by
which monster landed in a given fight room this session. GridMap can't reference D20System's
`Monsters` dict (boundary violation) and `ICombatStatus` doesn't carry MaxHp. Fix: `Program.cs`
(composition root, boundary-exempt) computes a plain `IReadOnlyDictionary<int, int>` (room → that
room's assigned monster's MaxHp) — the same "push data down" constructor-injection pattern already
used for every other piece of Scenario data. No new Cartridge surface, no new GridMap→D20System
reference. Not called out in the spec's "otherwise unchanged" framing for GridMap's commands, but
forced once the roster becomes real.

## Implementation Approach

### Phase A: New Loot ROM project (`example/D20SystemExampleD`, `LunaFlow.Rom.Loot`)

New `.csproj`, same shape as the other three `example/` projects — references `LunaFlow.Rom`,
`LunaFlow.Rules`, `LunaFlow.Engine`, `D20SystemExampleC` (the Cartridge contract surface); **zero**
reference to `D20SystemExampleA`/`B`. Added to `LunaFlow_A.sln` as a fifth project entry (mechanical
GUID registration, matching the existing four `example/*` entries).

- **`Facts.cs`**:
  - `MonsterLootTable(IReadOnlyDictionary<string,string> ItemIdByMonsterId)` — static,
    constructor-injected, per spec.
  - `LootAssignment(int RoomId, string ItemId)`, `ItemAwarded(string ItemId, int RoomId)` — exactly
    as specced.
  - `LootPickupText(string ItemId, string Text)` — **addition**, same shape/reasoning as
    `RoomChallengePrompt`/`GameEndAnnouncement` (ticket 0043's generalized rule: "the fact a
    generated rule matches always carries resolved text, never a key"). The spec's award-rule
    pseudocode says "announce pickup flavor for `award.ItemId`" without naming a mechanism; this is
    the only DI-seam-respecting way to do it. Seeded once per item (5 total) from
    `flavorText["item-{id}-pickup"]`.
- **`LootRom.cs`**: `LootRom : IRom`. `Provides => []`; `Requires => [new
  Capability("ChallengeSolved", typeof(IChallengeSolved))]`. Constructor takes `MonsterLootTable`.
  `Name`/`Credits`/`Reference` boilerplate matches `GridMapRom`/`D20SystemRom`'s existing pattern
  (private nested `ILunaFlowReference` impl).
- **`Rules/LootRuleGroup.cs`**: `[RuleGroup("Loot")]`, one `[RuleTemplate]`:
  `Match<IChallengeSolved>` + `Match<LootAssignment>(a => a.RoomId == solved.RoomId)` +
  `Match<LootPickupText>(lp => lp.ItemId == award.ItemId)` + `Not<ItemAwarded>(ia => ia.RoomId ==
  solved.RoomId)` → `Insert(ItemAwarded)` + `Announce(pickup.Text)`. Same `RulePrototype`/
  `WhenStatements`/`ThenStatements` shape as `D20SystemRuleGroup`/`GridMapRuleGroup`.
- **`Handlers/InventoryCommandHandler.cs`**: constructor takes only `IReadOnlyDictionary<string,
  string> flavorText`. Reads `Query<ItemAwarded>()` only — no other fact type, no cross-ROM read.
  Empty → `flavorText["inventory-empty"]`; else → `flavorText["inventory-header"]` then each item's
  `flavorText["item-{id}-name"]`.

### Phase B: D20System changes (`example/D20SystemExampleA`)

- **`Facts.cs`**: `RoomChallenge` gains `string? MonsterId` (null for SkillCheck rooms).
  `MonsterTemplate` changes from `(CombatantStats Stats)` to `(string Id, string Name, string
  DescriptionKey, CombatantStats Stats)`. `RoomSolved`/`CombatRound`/`RoomFailed`/
  `RoomChallengePrompt` unchanged.
- **`D20SystemRom.cs`**: constructor param `MonsterTemplate monster` → `IReadOnlyDictionary<string,
  MonsterTemplate> monsters`; property `Monster` → `Monsters`. `PlayerCharacter`/`Challenges`/
  `PlayerAbilityScores`/`Mechanic` unchanged.
- **`Handlers/FightCommandHandler.cs`**: resolves `_d20System.Challenges[location.RoomId].MonsterId`
  → `_d20System.Monsters[monsterId].Stats` wherever the old single `_d20System.Monster.Stats` was
  read (fresh-round MaxHp seed, Defense/AttackBonus/DamageDie/DamageBonus). Combat mechanic itself
  (attack rolls, lethality-first ordering, 3-round clock) untouched.
- **`Rules/D20SystemRuleGroup.cs`**: no change (deviation #1).
- **`Handlers/CheckCommandHandler.cs`**: no change — already reads `_d20System.Challenges` by room id.

### Phase C: GridMap changes (`example/D20SystemExampleB`)

Only `Handlers/LookCommandHandler.cs`: constructor param `int monsterMaxHp` →
`IReadOnlyDictionary<int, int> monsterMaxHpByRoom`, looked up by `current.RoomId` when reporting
combat status (deviation #2). No other GridMap file touched — `MoveCommandHandler`,
`GridMovementService`, `Facts.cs`, `GridMapRom.cs`, `GridMapRuleGroup.cs` all untouched, per spec's
explicit "any change to GridMap... untouched by this entire spec."

### Phase D: Cartridge contract surface (`example/D20SystemExampleC`)

Untouched. No new interfaces — Loot provides nothing, so nothing needs a contract to consume from it.

### Phase E: Rulebook content (`src/LunaFlow.Rulebook/OneD20`)

- **`OneD20ScenarioData.cs`**: `OneD20RoomData` trimmed to grid position + which slot-kind it is
  (fixed, never randomized): `(int Id, int Row, int Col, OneD20ChallengeType ChallengeType, string
  DescriptionKey)`. New `OneD20ChallengeTemplate(string Key, string Skill, string SkillAbility, int
  DC, string SuccessKey, string FailureKey, string PromptKey)` — the 9-entry pool (all SkillCheck;
  Fight slots are represented purely by monster assignment, matching today's shape where fight rooms
  already carry all-null skill fields). New `OneD20MonsterTemplate(string Id, string Name, string
  DescriptionKey, OneD20CombatantStats Stats)` — the 5-entry roster, replacing the singleton
  `Monster`.
- **`OneD20RulebookContent.cs`**: `Rooms` keeps 9 fixed grid entries (Row/Col/ChallengeType/
  DescriptionKey only now). New `Challenges: IReadOnlyDictionary<string, OneD20ChallengeTemplate>`
  (9 entries, keyed `search`/`climb`/`listen`/`swim`/`disabledevice`/`jump`/`balance`/`spot`/
  `concentration`, per the flavor doc's rekey). New `Monsters: IReadOnlyDictionary<string,
  OneD20MonsterTemplate>` (5 entries: `duelist`/`brawler`/`marksman`/`enforcer`/`scrapper`, stats
  from the spec's table). New `ItemIdByMonsterId: IReadOnlyDictionary<string,string>` (5 entries,
  from the spec's monster→item table). `PlayerCharacter`/`PlayerAbilityScores` unchanged.
- **New `OneD20SessionAssembler.cs`**: pure Rulebook-tier data transform — no Engine/NRules touch (no
  `ICommandHandler`, no `LunaFlowEngine.Host`, no fact-store access, satisfying the authored-content
  boundary in `engine-core.md`). `OneD20SessionAssembler(Random? random = null)`, defaulting to a
  real `Random` — same injectable seam as ticket 0019's `D20ResolutionMechanic`. `Assemble()` returns
  `OneD20SessionAssignment(IReadOnlyDictionary<int,string> ChallengeKeyByRoom,
  IReadOnlyDictionary<int,string> MonsterIdByRoom, IReadOnlyDictionary<int,string> ItemIdByRoom)`:
  shuffles the 9 challenge keys, takes 6, zips onto the fixed skill-check room ids (derived from
  `Rooms` where `ChallengeType == SkillCheck`, not re-hardcoded); shuffles the 5 monster ids, takes
  3, zips onto the fixed fight room ids; derives `ItemIdByRoom` from step 2's monster assignment +
  `ItemIdByMonsterId`.
- **`OneD20FlavorText.cs`**: rewritten per the flavor spec's exact tables (transcribed verbatim, no
  invention) — drop room-indexed `room-N-prompt`/`check-N-success`/`check-N-failure` keys; add the 9
  challenge-indexed `{key}-prompt`/`{key}-success`/`{key}-failure` triples (27 keys); replace
  `monster-desc` with 5 `monster-{id}-desc` keys; reword `monster-defeated`/`monster-hit` (generic,
  no weapon-specific bleed); add 5 `item-{id}-name` + 5 `item-{id}-pickup` keys; add
  `inventory-empty`/`inventory-header`. Room `room-N-desc` keys and unchanged combat lines carry over
  verbatim.
- **`OneD20RuleBook.cs`**: `DependsOnRoms` → `{ "GridMap", "D20System", "Loot" }`.

### Phase F: Composition root (`src/MyLunaFlowServer/Program.cs`)

- Construct `new OneD20SessionAssembler().Assemble()` as the first statement inside `Bootstrap()`
  (before `ConstructGridMap()`) — a plain Rulebook-tier data type with no ROM/Cartridge type
  reference, so it doesn't affect the existing JIT-failure-isolation property the surrounding comment
  documents. Thread the resulting `OneD20SessionAssignment` into `ConstructD20System(assignment)` and
  a new `ConstructLoot(assignment)`, same isolated-static-method pattern as `ConstructGridMap`.
- `ConstructD20System`: for each of the 9 fixed rooms, build `RoomChallenge` from either the assigned
  pool challenge (skill-check rooms) or the assigned `MonsterId` (fight rooms); build the full
  5-entry `Monsters` dict (translated from `OneD20RulebookContent.Monsters`) — always all 5, since
  whichever 3 are in play this session still need to resolve.
- `ConstructLoot`: builds `LootRom` from the full 5-entry `MonsterLootTable` (translated from
  `OneD20RulebookContent.ItemIdByMonsterId`). Registered in `Bootstrap()`'s `ComponentRegistry` as a
  third component (`EngineTier.Rom`, name `"Loot"`), added to the existing `Provides`-probing loop
  (empty `Provides` — loop handles that naturally, no special-casing needed).
- `RunGame`: seed `LootAssignment` facts (from `assignment.ItemIdByRoom`) and 5 `LootPickupText`
  facts (`flavorText["item-{id}-pickup"]`, all 5 regardless of session — harmless, the award rule
  only fires when a matching `LootAssignment` also exists) alongside the existing
  `RoomChallengePrompt`/`GameEndAnnouncement` seed block. `RoomChallengePrompt` seeding for fight
  rooms now resolves `flavorText[Monsters[assignment.MonsterIdByRoom[roomId]].DescriptionKey]`
  instead of the fixed `flavorText["monster-desc"]` (deviation #1); skill-check rooms unchanged.
  Register `RuleExport.Compile(typeof(LootRuleGroup))` alongside the other two rule groups. Register
  `inventory`/`inv` → `InventoryCommandHandler`, same dual-alias pattern as `quit`/`exit`. Build the
  new `monsterMaxHpByRoom` dict for `LookCommandHandler` (deviation #2).

## Known Edge Cases & Decisions

1. **`ChallengePromptRule` mechanism vs. the spec's literal text** — see Deviation #1 above. Ticket
   to Amara at handoff; not blocking, since the behavior matches and no framework gap is involved.
2. **`LookCommandHandler`'s monster-max-HP scalar → dict** — see Deviation #2 above. Forced by the
   roster, not spec'd explicitly; same push-down pattern as everything else Program.cs injects.
3. **`LootPickupText` is a new fact type not named in the spec** — direct application of ticket
   0043's already-generalized ruling to the one place this spec needed resolved text inside generated
   rule code. Not a new pattern, just its second use.
4. **Full 5-monster/5-item tables always constructed, even though only 3 monsters play a given
   session** — `D20SystemRom.Monsters` and `LootRom`'s `MonsterLootTable` both hold all 5 always;
   only `RoomChallenge.MonsterId` assignment (3 of 5) and `LootAssignment` facts (3 of 5, one per
   fight room) are session-scoped. Simpler than conditionally trimming the static tables, and
   `FightCommandHandler` needs to resolve whichever 3 actually got assigned.
5. **`tests/` compile break is expected, not fixed here** — per the confirmed scope boundary; flagged
   to Nadia in the done-bar ticket, same as 0037 → 0038 → 0044.

## Verification Strategy

1. `dotnet build LunaFlow_A.sln` — expect `src/`+`example/` to build clean; `tests/LunaFlow.EngineTests`
   may fail to compile against the new shapes (expected, not fixed in this pass).
2. `dotnet run --project src/MyLunaFlowServer` — play at least two full sessions end-to-end:
   - Room→challenge and room→monster assignment differs between runs (randomization is real).
   - Each fight room announces its assigned monster's own arrival text.
   - Defeating a monster inserts exactly one `ItemAwarded` matching that monster's loot-table entry;
     `inventory`/`inv` lists it by name.
   - A lost/fled fight awards nothing.
   - Skill-check rooms never award loot (check across enough sessions to sample the 9-challenge
     pool).
   - Room *type* topology (fight positions 1/5/8, combat-free win line `[3,6,9]`) is identical across
     every run.
   - Removing the Loot ROM from registration produces a clear load-time error (assembly-graph +
     registry check, same bar as GridMap/D20System).
3. Assembly-graph check: `D20SystemExampleD.csproj` has zero reference to `D20SystemExampleA`/`B`.

## Risk & Mitigation

| Risk | Mitigation |
|------|-----------|
| `RoomChallengePrompt` seeding logic silently reverts to fixed `"monster-desc"` text for fight rooms | Verify by playing ≥2 sessions with different seeds and confirming the announced text differs per assigned monster |
| Static 5-entry tables (`Monsters`, `MonsterLootTable`) and session-scoped 3-entry assignments get conflated | Keep `OneD20SessionAssembler`'s output (`OneD20SessionAssignment`) as the only session-scoped data; static pools stay in `OneD20RulebookContent` untouched by randomization |
| `tests/` compile break blocks a build-verification step I rely on | Verify `src/`+`example/` projects individually if `dotnet build` on the full `.sln` fails on `tests/` |
| `LootRuleGroup`'s award rule fires for skill-check rooms by accident | Guaranteed by construction: skill-check rooms never get a `LootAssignment` fact seeded, so `Match<LootAssignment>` never matches for them — verify across all 9 pool challenges during manual test |
| Deviations #1/#2 read as silent spec drift instead of reasoned calls | Both documented here and restated explicitly in the done-bar ticket to Kofi/Amara |

## Summary

- **New project**: `example/D20SystemExampleD` (`LunaFlow.Rom.Loot`) — pure-sink ROM, zero reference
  to GridMap/D20System, added to `LunaFlow_A.sln`.
- **D20System**: roster (`MonsterTemplate` keyed, `RoomChallenge.MonsterId`), `FightCommandHandler`
  resolves per-room monster. No rule-shape change (deviation #1).
- **GridMap**: one handler signature change only (`LookCommandHandler`, deviation #2). Everything
  else untouched.
- **Cartridge contract surface**: untouched — Loot needs no new published interface.
- **Rulebook**: content restructured (grid/challenge-pool/monster-roster split), new
  `OneD20SessionAssembler` with injectable `Random` (ticket 0019's seam), flavor text rekeyed per the
  companion doc, `DependsOnRoms` grows a third entry.
- **Composition root**: session assembly happens once per bootstrap, threaded into both new ROM
  constructions; new facts seeded (`LootAssignment`, `LootPickupText`); `inventory`/`inv` registered.
- **Out of scope, flagged for follow-up**: `tests/` suite fix (Nadia), the two mechanism deviations
  (Amara) — both raised in the done-bar ticket to Kofi, not resolved here.

## Context

Phase 2.8 is Rulebook-tier restructuring only — no new framework capability, no `ComponentRegistry`
change, no ROM fact-shape change. It splits `OneD20RulebookContent`/`OneD20FlavorText`'s static
surface into a `IOneD20WorldModule` contract (Rulebook-owned) plus `DefaultOneD20WorldModule` (an
instance implementing it, carrying today's shipped content verbatim), decouples
`OneD20SessionAssembler` from the statics, adds a load-time validation pass at the boundary, and now
also builds `HollowKeepWorldModule`, the second, independently-authored implementation that proves
the swap is real.

Confirmed with Kofi (PM) before starting:
1. `DefaultOneD20WorldModule`'s file layout carries forward today's split: a partial class across two
   files, mirroring `OneD20RulebookContent`/`OneD20FlavorText`'s existing split, to keep the diff
   verifiable by direct comparison against the old statics.
2. The validation pass is a standalone class (`OneD20WorldModuleValidator`), not a method folded onto
   an existing type.

**New since first draft:** Hollow Keep's content is ready (0059 in-review, ticket 0061 already fixed
the flavor file's key-prefix bug), so this build folds it in rather than deferring — the ticket's own
"don't block starting on it" language is about not *waiting*, not about excluding it once it exists.

## Implementation Approach

### Phase A: The contract — `IOneD20WorldModule.cs`

New interface in `LunaFlow.Rulebook.OneD20`, exactly the shape the spec and `world-module.md` both
give: `Rooms`, `StartRoomId`, `Challenges`, `Monsters`, `ItemIdByMonsterId`, `PlayerCharacter`,
`PlayerAbilityScores`, `FlavorText`. Every property is today's `OneD20RulebookContent`/
`OneD20FlavorText` static surface, moved to instance members — no new shape, no rename. The existing
Rulebook-owned records (`OneD20RoomData`/`OneD20ChallengeTemplate`/`OneD20MonsterTemplate`/
`OneD20CombatantStats` in `OneD20ScenarioData.cs`) are untouched; a World Module populates them, it
doesn't redefine them. *(Already written — matches this plan unchanged.)*

### Phase B: `DefaultOneD20WorldModule` — partial class, two files

- **`DefaultOneD20WorldModule.cs`**: `Rooms`/`StartRoomId`/`Challenges`/`Monsters`/
  `ItemIdByMonsterId`/`PlayerCharacter`/`PlayerAbilityScores`, values transcribed verbatim from
  `OneD20RulebookContent`'s current static fields.
- **`DefaultOneD20WorldModule.FlavorText.cs`**: `FlavorText`, values transcribed verbatim from
  `OneD20FlavorText.Text`.
- Verification for the "reproduces today's exact shipped content" acceptance criterion: diff each
  transcribed table against the current file content line-for-line before deleting the old statics
  (Phase E).

### Phase C: `OneD20WorldModuleValidator.cs` — standalone validator

`public static class OneD20WorldModuleValidator { public static void Validate(IOneD20WorldModule module) }`.
Fail-fast: throws `InvalidOperationException` on the first violated check, message names what's
wrong. Checks, translating the spec's Mechanics/Validation bullets (as amended 2026-08-03) into
concrete rules:

1. `Rooms` has exactly the 9 keys `1..9`.
2. `Challenges.Count >= 6` and `Monsters.Count >= 3` (the grid's fixed slot counts).
3. The room-type counts actually derived from `Rooms` fit their respective pools — `SkillCheck` room
   count `<=` `Challenges.Count`, `Fight` room count `<=` `Monsters.Count`. (Coincides with check 2
   for today's fixed topology; kept separate because it's what the spec's "fillable from Challenges"
   bullet is actually asking, and it's the check that generalizes if room type ever varies.)
4. Every `OneD20ChallengeTemplate`/`OneD20MonsterTemplate`'s flavor keys (`PromptKey`/`SuccessKey`/
   `FailureKey`/`DescriptionKey`) resolve in `FlavorText`. **Judgment call beyond the spec's literal
   list, unchanged from the first draft:** also checking each `OneD20RoomData.DescriptionKey`
   resolves — same failure mode, same boundary. Flagged here in case Amara wants it split out.
5. `PlayerAbilityScores` names all six abilities (`Str`/`Dex`/`Con`/`Int`/`Wis`/`Cha`).
6. **New (spec amendment, 2026-08-03):** `FlavorText` contains, verbatim and unprefixed, all eleven
   fixed-vocabulary keys every command handler reads as a hardcoded literal rather than through a
   template's `*Key` field: `pc-hit`, `pc-miss`, `monster-hit`, `monster-miss`, `monster-defeated`,
   `monster-fled`, `pc-flee`, `pc-lost`, `win-announce`, `inventory-empty`, `inventory-header`. This
   is the check ticket 0061 found missing — without it, a module that namespaces these under its own
   prefix (exactly the mistake Hollow Keep's flavor file first made) passes every other check and then
   throws `KeyNotFoundException` mid-session on the first successful hit/flee/win/inventory check
   instead of failing at load.

### Phase D: Decouple `OneD20SessionAssembler`

Constructor becomes `OneD20SessionAssembler(IOneD20WorldModule worldModule, Random? random = null)`.
`Assemble()` reads `Rooms`/`Challenges`/`Monsters`/`ItemIdByMonsterId` from the injected
`_worldModule` instead of `OneD20RulebookContent`'s statics. The shuffle-and-slot algorithm itself is
unchanged — only its input source. Grepping the file for `OneD20RulebookContent`/`OneD20FlavorText`
by name must return zero hits afterward (acceptance criterion).

### Phase E: Retire the static surface

Delete `OneD20RulebookContent.cs` and `OneD20FlavorText.cs` once Phases B–D compile clean against the
new contract, and once Phase F (below) has repointed every reader.

### Phase F: `Program.cs` — one new input, same translation path

- `Bootstrap()` constructs `IOneD20WorldModule worldModule = new DefaultOneD20WorldModule();`,
  immediately calls `OneD20WorldModuleValidator.Validate(worldModule)` — before anything else touches
  it — then `new OneD20SessionAssembler(worldModule).Assemble()`. Same no-ROM/Cartridge-type-at-this-
  scope isolation reasoning the surrounding comment already documents.
- `ConstructGridMap`/`ConstructD20System`/`ConstructLoot` each gain a `worldModule` parameter, read
  `worldModule.Rooms`/`.Challenges`/`.Monsters`/`.ItemIdByMonsterId`/`.PlayerCharacter`/
  `.PlayerAbilityScores` instead of `OneD20RulebookContent`'s statics.
- `RunGame` gains a `worldModule` parameter, reads `worldModule.PlayerCharacter`/`.Rooms`/
  `.Monsters`/`.ItemIdByMonsterId`/`.FlavorText` wherever it currently reads
  `OneD20RulebookContent`/`OneD20FlavorText.Text`.
- The existing `catch (InvalidOperationException ex)` block's message
  (`"Component registry validation failed: {ex.Message}"`) is now misleading, since
  `OneD20WorldModuleValidator` can also throw `InvalidOperationException` before the registry is ever
  touched. Generalize the message (e.g. `"Validation failed: {ex.Message}"`).
- **The World Module choice stays a single, clearly-marked compile-time line** — `new
  DefaultOneD20WorldModule()` ships as the active choice (matches today's behavior; no
  player-visible change per the spec's own "Supersedes: nothing"), with `HollowKeepWorldModule` as
  the documented, one-line alternative to swap in — same "no loader" deferral both specs name. Used
  for manual proof (Phase G/Verification), not left switched on.

### Phase G (new): `HollowKeepWorldModule` — the second implementation

Content transcribed verbatim from `1-d20-worldmodule-hollow-keep-spec.md`'s tables and
`1-d20-worldmodule-hollow-keep-flavor.md`'s prose (already `hk-`-prefixed and, per ticket 0061,
already correct on the eleven fixed-vocabulary keys — nothing to re-fix on my side). Same file split
as `DefaultOneD20WorldModule` for consistency: `HollowKeepWorldModule.cs` (rooms/challenges/
monsters/loot/PC/ability scores) + `HollowKeepWorldModule.FlavorText.cs` (flavor text). **Placement
call:** lives alongside `DefaultOneD20WorldModule` in `LunaFlow.Rulebook.OneD20` — no new project. A
World Module is "one thing: a class" per `world-module.md`; nothing in either spec asks for a
separate assembly, and inventing one now would be exactly the kind of speculative generalization
`non-goals.md`'s discipline argues against. Revisit only if a real second-project need shows up later.

Room/challenge/monster/PC/ability values are byte-for-byte identical to `DefaultOneD20WorldModule`'s
per the Hollow Keep spec's own acceptance criteria (only names/descriptions/flavor differ) — verified
by comparing the two modules' numeric fields, not just eyeballing "looks close."

## Known Edge Cases & Decisions

1. **`tests/LunaFlow.ContentTests` will fail to compile** once `OneD20RulebookContent`/
   `OneD20FlavorText` are deleted — confirmed by grep: five files reference them directly
   (`OneD20SessionAssemblerTests.cs`, `ComponentRegistryContentTests.cs`,
   `InventoryCommandHandlerTests.cs`, `D20SystemRuleFixtureTests.cs`, `D20SystemHandlerTests.cs`),
   heavily, not incidentally. Same scope boundary as every prior content phase (2-7-1's CodePlan,
   ticket 0034 → 0037 → 0038 → 0044): Baraka doesn't edit `tests/`. Ship `src/` to spec, flag a
   follow-up ticket to Nadia (Test Dev) to repoint these fixtures at `IOneD20WorldModule`/
   `DefaultOneD20WorldModule`. The spec's own last acceptance item ("full suite green") is gated on
   that follow-up landing, not on this pass.
2. **Validator check 4's room-`DescriptionKey` coverage goes slightly beyond the spec's literal
   bullet list** — recorded in Phase C, will be called out explicitly in the done-bar response to
   Kofi, not silently added.
3. **Validator checks 2 and 3 overlap for today's fixed 6-skill-check/3-fight topology** — kept as
   two separate checks anyway; different things tested, spec lists them as separate bullets.
4. **`HollowKeepWorldModule` lives in the same project/namespace as `DefaultOneD20WorldModule`**, not
   a separate assembly — Phase G's placement call, consistent with both specs' silence on needing one.
5. **Both World Modules built, only one shipped active** — `Program.cs` keeps a single compile-time
   line choosing `DefaultOneD20WorldModule`; `HollowKeepWorldModule` is proven by temporarily swapping
   that line during verification, not by adding a runtime switch (no loader exists or is being built).

## Verification Strategy

1. `dotnet build LunaFlow_A.sln` — expect `src/` to build clean; `tests/LunaFlow.ContentTests` is
   expected to fail to compile (edge case 1) — verify `src/` in isolation if the full-solution build
   fails there.
2. Diff `DefaultOneD20WorldModule`'s transcribed tables against the pre-deletion
   `OneD20RulebookContent`/`OneD20FlavorText` content (Phase B) before Phase E deletes the originals.
   Diff `HollowKeepWorldModule`'s numeric fields (DCs, stats, ability scores) against
   `DefaultOneD20WorldModule`'s for byte-for-byte equality per Hollow Keep's own acceptance criteria.
3. `dotnet run --project src/MyLunaFlowServer` with `DefaultOneD20WorldModule` active — play a full
   session end-to-end: move/look/check/fight/flee/inventory all work, win-line topology (rooms 3/6/9)
   unaffected, loot awards correctly, room 5's start announcement fires. Run at least twice to confirm
   randomization still varies room→challenge/monster assignment.
4. Swap the compile-time line to `HollowKeepWorldModule`, repeat step 3's full session — this is the
   phase's actual Done-When bar. Swap back to `DefaultOneD20WorldModule` afterward.
5. Demonstrate the validator rejecting **two** distinct broken-module scenarios (both acceptance
   criteria are separately listed and need separate proof): (a) a structural gap — e.g. a missing
   room or a `Challenges` pool of 5 — and (b) a fixed-vocabulary gap — e.g. a module that
   (re-)namespaces `win-announce`. Confirm a clear, load-time, non-zero-exit error naming what's
   wrong in each case, not a downstream `KeyNotFoundException` mid-session.

## Risk & Mitigation

| Risk | Mitigation |
|------|-----------|
| Transcription typo in either World Module silently changes shipped/spec'd content | Diff against source tables before deleting the old statics (Phase B/E) and cross-diff the two modules' numeric fields (Phase G) |
| Validator's extra `DescriptionKey` check (edge case 2) reads as scope creep | Called out explicitly here and in the done-bar response, not silently added |
| `tests/` compile break blocks a build-verification step relied on elsewhere | Verify `src/` in isolation; flag the follow-up ticket to Nadia rather than touching `tests/` |
| Fixed-vocabulary check (new) only gets exercised against `DefaultOneD20WorldModule`, missing the exact bug 0061 found in Hollow Keep's *original* draft | Verify against a throwaway broken module with an `hk-`-style re-prefixed fixed key, not just against the now-fixed Hollow Keep content |
| `Program.cs`'s existing `catch (InvalidOperationException)` message becomes misleading once two different validators can throw it | Generalized in Phase F |

## Summary

- **New**: `IOneD20WorldModule` contract, `DefaultOneD20WorldModule` + `HollowKeepWorldModule` (both
  partial classes, same file-split convention), `OneD20WorldModuleValidator` (standalone, fail-fast,
  six checks including the new fixed-vocabulary one).
- **Changed**: `OneD20SessionAssembler` takes the World Module instead of reading statics;
  `Program.cs` constructs/validates/threads it through, same translation path otherwise; one
  documented compile-time swap point for which module ships.
- **Deleted**: `OneD20RulebookContent.cs`, `OneD20FlavorText.cs`.
- **In scope now (changed from first draft)**: the second World Module (Hollow Keep) — content was
  delivered mid-plan, so this pass builds and exercises it rather than deferring, aiming to actually
  clear Phase 2.8's Done-When bar.
- **Out of scope, flagged for follow-up**: `tests/` suite repointing (Nadia) — raised in the done-bar
  ticket to Kofi, not resolved here.

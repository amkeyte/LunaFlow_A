# Phase 2.8 Implementation Plan: World Module Extraction

**Ticket:** [0060](../../ClaudeWiki/Processes/Handoffs/0060-implement-world-module-extraction-spec-md.md)
**Spec:** [`world-module-extraction-spec.md`](../../Specs/world-module-extraction-spec.md)

**Related:** [0059](../../ClaudeWiki/Processes/Handoffs/0059-second-world-module-reskin-content.md) — Juno's second, independently-authored `IOneD20WorldModule`, running alongside this build, not gating its start.

## Context

Phase 2.8 is Rulebook-tier restructuring only — no new framework capability, no `ComponentRegistry`
change, no ROM fact-shape change. It splits `OneD20RulebookContent`/`OneD20FlavorText`'s static
surface into a `IOneD20WorldModule` contract (Rulebook-owned) plus `DefaultOneD20WorldModule` (an
instance implementing it, carrying today's shipped content verbatim), decouples
`OneD20SessionAssembler` from the statics, and adds a load-time validation pass at the boundary.

Confirmed with Kofi (PM) before starting:
1. Items 1–4 (contract, default implementation, decoupled assembler, validation pass) start now;
   item 5 (the second, independently-authored `IOneD20WorldModule`) is Juno's content call under
   0059 and doesn't gate starting — only gates closing 0060, per the ticket's own text.
2. `DefaultOneD20WorldModule`'s file layout carries forward today's split: a partial class across two
   files, mirroring `OneD20RulebookContent`/`OneD20FlavorText`'s existing split, to keep the diff
   verifiable by direct comparison against the old statics.
3. The validation pass is a standalone class (`OneD20WorldModuleValidator`), not a method folded onto
   an existing type — matches the spec's own suggested name, keeps it separately greppable.

## Implementation Approach

### Phase A: The contract — `IOneD20WorldModule.cs`

New interface in `LunaFlow.Rulebook.OneD20`, exactly the shape the spec and `world-module.md` both
give: `Rooms`, `StartRoomId`, `Challenges`, `Monsters`, `ItemIdByMonsterId`, `PlayerCharacter`,
`PlayerAbilityScores`, `FlavorText`. Every property is today's `OneD20RulebookContent`/
`OneD20FlavorText` static surface, moved to instance members — no new shape, no rename. The existing
Rulebook-owned records (`OneD20RoomData`/`OneD20ChallengeTemplate`/`OneD20MonsterTemplate`/
`OneD20CombatantStats` in `OneD20ScenarioData.cs`) are untouched; the World Module populates them, it
doesn't redefine them.

### Phase B: `DefaultOneD20WorldModule` — partial class, two files

- **`DefaultOneD20WorldModule.cs`**: `Rooms`/`StartRoomId`/`Challenges`/`Monsters`/
  `ItemIdByMonsterId`/`PlayerCharacter`/`PlayerAbilityScores`, values transcribed verbatim from
  `OneD20RulebookContent`'s current static fields — a relocation, not a rewrite.
- **`DefaultOneD20WorldModule.FlavorText.cs`**: `FlavorText`, values transcribed verbatim from
  `OneD20FlavorText.Text`.
- Verification for the "reproduces today's exact shipped content" acceptance criterion: diff each
  transcribed table against the current file content line-for-line before deleting the old statics
  (Phase E), not just a shape/count match.

### Phase C: `OneD20WorldModuleValidator.cs` — standalone validator

`public static class OneD20WorldModuleValidator { public static void Validate(IOneD20WorldModule module) }`.
Fail-fast: throws `InvalidOperationException` on the first violated check, message names what's
wrong — same "hard fail at bootstrap, never a degradation during play" property `ComponentRegistry`
holds one tier over (per `engine-core.md`). Checks, translating the spec's Mechanics/Validation bullets
into concrete rules:

1. `Rooms` has exactly the 9 keys `1..9`.
2. `Challenges.Count >= 6` and `Monsters.Count >= 3` (the grid's fixed slot counts).
3. The room-type counts actually derived from `Rooms` fit their respective pools — `SkillCheck` room
   count `<=` `Challenges.Count`, `Fight` room count `<=` `Monsters.Count`. (For the default topology
   this coincides with check 2; it's kept as its own check because it's what the spec's "every
   SkillCheck room's position is fillable from Challenges" bullet is actually asking, and it's the
   check that generalizes if a second World Module ever varies which rooms are which type.)
4. Every `OneD20ChallengeTemplate`/`OneD20MonsterTemplate`'s flavor keys (`PromptKey`/`SuccessKey`/
   `FailureKey`/`DescriptionKey`) resolve in `FlavorText`. **Judgment call beyond the spec's literal
   list:** also checking each `OneD20RoomData.DescriptionKey` resolves — same failure mode
   (`Program.cs` reads it unchecked today), same boundary, and the spec's own rationale sentence
   ("a missing key fails at load, not as a blank announcement mid-session") isn't scoped to only
   challenge/monster keys. Flagging here in case Amara wants it split out.
5. `PlayerAbilityScores` names all six abilities (`Str`/`Dex`/`Con`/`Int`/`Wis`/`Cha`).

### Phase D: Decouple `OneD20SessionAssembler`

Constructor becomes `OneD20SessionAssembler(IOneD20WorldModule worldModule, Random? random = null)`.
`Assemble()` reads `Rooms`/`Challenges`/`Monsters`/`ItemIdByMonsterId` from the injected
`_worldModule` instead of `OneD20RulebookContent`'s statics. The shuffle-and-slot algorithm itself is
unchanged — only its input source. Grepping the file for `OneD20RulebookContent`/`OneD20FlavorText`
by name must return zero hits afterward (acceptance criterion).

### Phase E: Retire the static surface

Delete `OneD20RulebookContent.cs` and `OneD20FlavorText.cs` once Phases B–D compile clean against the
new contract, and once Phase F (below) has repointed every reader.

### Phase F: `Program.cs` — one new input, same translation path

- `Bootstrap()` constructs `IOneD20WorldModule worldModule = new DefaultOneD20WorldModule();`,
  immediately calls `OneD20WorldModuleValidator.Validate(worldModule)` — before anything else touches
  it, per the spec — then `new OneD20SessionAssembler(worldModule).Assemble()`. Same
  no-ROM/Cartridge-type-at-this-scope isolation reasoning the surrounding comment already documents:
  `IOneD20WorldModule`/`DefaultOneD20WorldModule`/the validator are plain Rulebook-tier types, so
  constructing/validating them here doesn't affect the existing JIT-failure-isolation property.
- `ConstructGridMap`/`ConstructD20System`/`ConstructLoot` each gain a `worldModule` parameter, read
  `worldModule.Rooms`/`.Challenges`/`.Monsters`/`.ItemIdByMonsterId`/`.PlayerCharacter`/
  `.PlayerAbilityScores` instead of `OneD20RulebookContent`'s statics. Translation logic inside each
  (the `GridRoomData`/`RoomChallenge`/`MonsterTemplate`/`CombatantStats` construction) is unchanged.
- `RunGame` gains a `worldModule` parameter, reads `worldModule.PlayerCharacter`/`.Rooms`/
  `.Monsters`/`.ItemIdByMonsterId`/`.FlavorText` wherever it currently reads
  `OneD20RulebookContent`/`OneD20FlavorText.Text`.
- The existing `catch (InvalidOperationException ex)` block's message
  (`"Component registry validation failed: {ex.Message}"`) is now misleading, since
  `OneD20WorldModuleValidator` can also throw `InvalidOperationException` before the registry is ever
  touched. Generalize the message (e.g. `"Validation failed: {ex.Message}"`) — `ex.Message` already
  names what's wrong in both cases.

## Critical Files to Modify/Create

**New** (`src/LunaFlow.Rulebook/OneD20/`):
- `IOneD20WorldModule.cs` — the contract
- `DefaultOneD20WorldModule.cs` — rooms/challenges/monsters/loot table/PC/ability scores
- `DefaultOneD20WorldModule.FlavorText.cs` — flavor text, partial-class companion to the above
- `OneD20WorldModuleValidator.cs` — standalone load-time validator

**Modified**:
- `OneD20SessionAssembler.cs` — constructor takes `IOneD20WorldModule`, reads from it instead of statics
- `src/MyLunaFlowServer/Program.cs` — construct + validate the World Module, thread it through
  `ConstructGridMap`/`ConstructD20System`/`ConstructLoot`/`RunGame`, generalize the validation-failure
  catch message

**Deleted**:
- `OneD20RulebookContent.cs`
- `OneD20FlavorText.cs`

**Untouched**: `OneD20ScenarioData.cs` (the record shapes — unchanged, per spec's explicit Scope/Out),
`OneD20RuleBook.cs` (`DependsOnRoms` unchanged), `OneD20RulebookReference.cs`, every ROM/Cartridge
project (`GridMap`/`D20System`/`Loot`), the Cartridge contract surface.

## Known Edge Cases & Decisions

1. **Item 5 (second World Module) is out of this pass** — tracked as 0059, Juno's content call. This
   ticket's own Ask says don't block starting on it; the Done-When bar for *closing* 0060 does need it
   (a full session run against Juno's module), so this ticket stays open after Phases A–F land, to be
   closed once 0059's content arrives and is exercised.
2. **`tests/LunaFlow.ContentTests` will fail to compile** once `OneD20RulebookContent`/
   `OneD20FlavorText` are deleted — confirmed by grep: five files reference them directly
   (`OneD20SessionAssemblerTests.cs`, `ComponentRegistryContentTests.cs`,
   `InventoryCommandHandlerTests.cs`, `D20SystemRuleFixtureTests.cs`, `D20SystemHandlerTests.cs`),
   heavily, not incidentally. Same scope boundary as every prior content phase (2-7-1's CodePlan,
   ticket 0034 → 0037 → 0038 → 0044): Baraka doesn't edit `tests/`. Ship `src/` to spec, flag a
   follow-up ticket to Nadia (Test Dev) to repoint these fixtures at `IOneD20WorldModule`/
   `DefaultOneD20WorldModule`. The spec's own last acceptance item ("full suite green") is gated on
   that follow-up landing, not on this pass.
3. **Validator check 4's room-`DescriptionKey` coverage goes slightly beyond the spec's literal
   bullet list** (see Phase C) — recorded here and will be called out explicitly in the done-bar
   response to Kofi, not silently added.
4. **Validator checks 2 and 3 overlap for today's fixed 6-skill-check/3-fight topology** — kept as
   two separate checks anyway because they test different things (a hardcoded floor vs. a
   count-derived-from-`Rooms` fit) and the spec lists them as separate bullets.

## Verification Strategy

1. `dotnet build LunaFlow_A.sln` — expect `src/` to build clean; `tests/LunaFlow.ContentTests` is
   expected to fail to compile (edge case 2, above) — verify `src/` in isolation if the full-solution
   build fails there.
2. `dotnet run --project src/MyLunaFlowServer` — play a full session end-to-end against
   `DefaultOneD20WorldModule`: move/look/check/fight/flee/inventory all work, win-line topology
   (rooms 3/6/9) unaffected, loot awards correctly, room 5's start announcement fires. Run at least
   twice to confirm randomization still varies room→challenge/monster assignment.
3. Demonstrate the validation pass rejecting a deliberately broken module (a throwaway test
   `IOneD20WorldModule` with, e.g., a `Challenges` pool of 5, or a missing room) — confirm a clear,
   load-time, non-zero-exit error naming what's wrong, not a downstream crash.
4. Diff `DefaultOneD20WorldModule`'s transcribed tables against the pre-deletion
   `OneD20RulebookContent`/`OneD20FlavorText` content (Phase B) before Phase E deletes the originals.

## Risk & Mitigation

| Risk | Mitigation |
|------|-----------|
| Transcription typo in `DefaultOneD20WorldModule` silently changes shipped content | Diff against the old statics before deleting them (Phase B/E ordering) |
| Validator's extra `DescriptionKey` check (edge case 3) reads as scope creep | Called out explicitly here and in the done-bar response, not silently added |
| `tests/` compile break blocks a build-verification step relied on elsewhere | Verify `src/` in isolation; flag the follow-up ticket to Nadia rather than touching `tests/` |
| `Program.cs`'s existing `catch (InvalidOperationException)` message becomes misleading once two different validators can throw it | Generalized in Phase F |

## Summary

- **New**: `IOneD20WorldModule` contract, `DefaultOneD20WorldModule` (partial class, today's split
  carried forward), `OneD20WorldModuleValidator` (standalone, fail-fast).

  `Program.cs` constructs/validates/threads it through, same translation path otherwise.
- **Deleted**: `OneD20RulebookContent.cs`, `OneD20FlavorText.cs`.
- **Out of scope, flagged for follow-up**: the second World Module (0059, Juno), `tests/` suite
  repointing (Nadia) — both raised in the done-bar ticket to Kofi, not resolved here.

## Deviations from spec / findings (informational, not blocking)

- **Test-coverage gaps in `OneD20WorldModuleValidatorTests.cs`, found by independent review, not the ticket's own claim.** The validator's *code* correctly implements every spec-listed check (confirmed above), but the *tests* pin only a representative subset: the fixed-vocabulary loop is tested for exactly 1 of its 11 keys (`win-announce`), the ability-score loop for exactly 1 of its 6 (`Con`), and the per-template flavor-key check for `PromptKey` only — `SuccessKey`/`FailureKey` have no dedicated test at all. None of this is tautological (each existing test does pin a real, distinct check with a specific error-message assertion), but a regression that dropped, say, `inventory-header` from the fixed-vocabulary list or the `Wis` check from the ability loop would pass CI silently today. Worth a ticket to Nadia to parameterize these three loops over their full lists rather than one representative each; not blocking this verdict since the mechanism itself is demonstrated working, live, for the case checked.
- `OneD20RuleBook.cs`'s single-line change (a stale `<see cref>` doc-comment pointing at the deleted static types, updated to point at the new ones) is worth naming explicitly since the spec's Done-When says "zero changes to Rulebook structural code" — this is the one file inside `LunaFlow.Rulebook` the phase's commit touched. Read the diff directly: it's prose only, not logic. Noting it rather than silently rounding it down to "zero files touched."
- Same open, pre-existing items noted in the Phase 2.7/2.7.1 verdicts (Phase 2.6.5 has no standalone QA verdict; `D20SystemContent` retained obsolete for NineRooms) still stand, unrelated to this phase, not re-litigated here.

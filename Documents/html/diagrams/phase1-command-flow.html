Phase 1 Command Flow — Signal Flow Visualizer

One typed console command, end to end, across the two threads that currently make up the ConsoleEngine + GameEngineCore path. Read top to bottom, or press Play to step through it. See engine-core.md for the prose version and the current dual-host caveat.

Main ThreadProgram.cs → ConsoleEngine
Background ThreadGameEngineCore.RunLoop
1Startup
Program.cs builds a ConsoleEngine, configures GameEngineOptions, and registers three handlers (quit, exit, echo) on the DefaultCommandDispatcher. Then it calls Run().
2Engine boot
ConsoleEngine.Run() subscribes to two GameEngineCore signals — MessagePosted (→ prints to console) and TurnTick (no-op, but keeps _turnTickSubs = 1) — then calls SetOptions() and Start().
new Thread(RunLoop).Start()
MessagePosted: "loop started…"
RunLoop begins
Background thread is alive, blocking on TryTake — no command queued yet.
3Read blocking
The foreground loop calls Console.ReadLine() and blocks until the user types a line.
4Parse (command pipeline)
Raw input → DefaultCommandParser.Parse() → DefaultCommand (splits into Name + Arguments).
5Signal: Submit → queue
The parsed command is wrapped in a DispatchGameCommand (bundled with a fresh ManualResetEventSlim) and pushed via GameEngineCore.Submit() into the BlockingCollection<IGameCommand> queue — the actual cross-thread signal from foreground → background.
Submit() — async
6Main thread blocks on completion
Immediately after submitting, the foreground thread calls completed.Wait() — it doesn't read the next line until the background thread confirms this command finished.
waiting on completed
7Background thread picks it up
RunLoop TryTakes the command off the queue and calls Execute(engine) inside ExecuteCommandSafe.
8Dispatch (command pipeline)
DispatchGameCommand.Execute calls ICommandDispatcher.Dispatch(), which looks up the handler by name:
  • echo → EchoCommandHandler writes the arguments to console.
  • unknown name → dispatcher itself prints "Unknown command: X".
  • quit/exit → QuitCommandHandler prints "Shutting down...", then calls GameEngineCore.RequestStop().
MessagePosted: "stop requested"
9Signal: RequestStop (non-blocking)
RequestStop() cancels the loop's CancellationToken, closes the queue (CompleteAdding), sets Running = false, and posts "GameEngine stop requested." back through MessagePosted — all synchronously, still on the background thread, without joining itself.
completed.Set() wakes Wait()
10Signal: completion → main thread wakes
Back in DispatchGameCommand.Execute's finally, completed.Set() fires — this is the signal that wakes the foreground thread's completed.Wait() from Step 6.
11Background thread exits
RunLoop's while condition (token.IsCancellationRequested) goes false on its next check; the loop breaks, its finally sets Running = false again (idempotent), and the OS thread terminates.
12Foreground loop exits, joins, shuts down
while (_engine.Running) is now false → the main thread calls _engine.Stop(), which Join()s the (already-finished) background thread and posts "GameEngine loop stopped."
13Process exit
Run() returns → Program.cs prints "Server stopped." → process exits (code 0).
Two signals worth telling apart: the queue submit (Step 5, foreground → background, async — fire it and move on to waiting) and the event/wait pair (Steps 6 + 9 + 10, the two ways the background thread talks back to the foreground: the broadcast MessagePosted channel, and the per-command completed handshake). Everything else in this flow is single-threaded control flow dressed up as a loop.
